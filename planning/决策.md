# 需求与决策记录

## 1. 项目定位

- **名称**: echomemory（回声记忆）
- **形态**: 本地 Windows 桌面客户端 + 云端 API 服务的 AI Agent 音乐平台

## 2. 技术栈

- **backend**: Python, FastAPI, Alembic, Pydantic, PostgreSQL（含 pgvector）, Redis, LangChain, LangGraph, RAG, OSS
- **frontend**: Tauri 2.x, React 19, TypeScript, Vite, Tailwind CSS

## 3. 约束

- 当前仅支持 Windows 桌面端。
- 前端由 AI 辅助生成，优先使用生态成熟、资料充足的技术。
- 需支持良好的动画效果。
- 优先保证内存安全、网络安全。
- 前端首期只开发亮色主题。
- 前端开发可按需新增成熟依赖，不需要逐项审批。
- **基础设施先行原则**：任何架构设计、基础设施（如 Nginx 反向代理、CORS 配置、日志目录等）必须在开发阶段尽早搭建完成，不允许以「等以后部署时再配」为由推迟。开发环境的架构应尽可能贴近生产环境。

## 4. 后端架构决策

- 开发环境使用两个 PostgreSQL 数据库：
  - `echomemory`：用于本地联调、模拟使用等场景。
  - `echomemory_test`：仅用于 pytest 单元测试和集成测试，测试框架强制替换连接指向该库。
- 后端采用全面异步架构：FastAPI + SQLAlchemy 2.0（`Mapped` / `mapped_column`） + `asyncpg` + `redis.asyncio`。
- 应用运行时全部使用异步数据库引擎；Alembic 迁移和测试初始化使用同步引擎（`psycopg2`）。
- 应用启动时通过 `lifespan` 自动执行 Alembic 升级到 `head`。
- 测试环境跳过 Alembic，通过 `Base.metadata.create_all/drop_all` 管理表结构。
- 测试使用 `FakeRedis` 替代真实 Redis。
- Python 版本为 3.12+，pytest 使用 `asyncio_mode = "auto"`。

## 5. 认证与授权

- 采用 JWT access token + Redis refresh token 双 token 机制。
- JWT 算法为 HS256，默认过期时间 1440 分钟（24 小时）。
- 登出时将 access token 写入 Redis 黑名单，黑名单 TTL 与 JWT 过期时间一致。
- 密码哈希使用 bcrypt，版本锁定 `<4.0`。
- 用户角色：`USER=0, VIP=1, ADMIN=2, SUPER_ADMIN=3`。
- 非 super-admin 不能修改、封禁或提升他人为 super-admin。
- 管理员不能对自己执行封禁、解禁或资料修改操作。
- 用户状态：`ACTIVE=0, TEMP_BAN=1, SUSPENDED=2, BANNED=3`。封禁时必须同时设置 `banned_at`，解封时清空 `banned_at` 和 `ban_duration`。

## 6. 数据持久化

- 主数据库为 PostgreSQL，并启用 `pg_trgm` 扩展用于 GIN 索引模糊查询。
- pgvector 作为向量数据库，用于支撑后续 RAG 场景。
- Alembic 负责数据库迁移，当前采用自动迁移模式。
- 大量业务约束下沉到数据库层：非负计数、角色/状态/性别范围、封禁时长为正、状态与 `banned_at` 一致性等。
- 用户等级由数据库触发器根据 `level_config` 表在 `exp` 变更时自动计算。
- 用户表使用软删除（`is_deleted`）；邮箱和手机采用部分唯一索引，允许 NULL，非空时必须唯一。
- 音乐没有软删除，删除通过下架（`is_published=False`）实现。
- 计数类字段反规范化存储：用户 `like_count`、音乐 `play_count` / `collect_count` / `comment_count`、专辑与歌单同类字段均直接存于主表。

## 7. 文件存储

- 使用阿里云 OSS 作为对象存储，Bucket 为公共读。
- 图片上传：初始文件最大 **20MB**，后端自动压缩至 **≤2MB**（JPEG，质量递减 + 尺寸缩放）后再发送至 OSS。
- 音频文件不压缩，最大 **30MB**，仅接受 MIME 类型：`audio/mpeg, audio/mp3, audio/flac, audio/wav, audio/x-wav, audio/ogg, audio/aac`。
- 歌词文件最大 **1MB**，仅接受 `text/plain` 和 `application/octet-stream`。
- OSS 客户端使用同步 SDK（`oss2`），异步接口通过 `anyio.to_thread.run_sync` 包装。
- 音乐导入过程中若后续步骤失败，回滚已上传的 OSS 文件。

## 8. 业务规则

- 音乐仅由管理员导入，普通用户不可创建。
- 音乐导入时禁止直接填写 URL，音频、封面、歌词均通过文件上传提供。
- 音乐的 `source` 字段由管理员自由填写，不设置枚举约束。
- 字典数据（styles、languages、instruments、emotion_tags、interest_tags）由管理员维护，普通用户只读。
- 用户居住城市（`city`）为自由填写的字符串字段，不由字典表维护；前端通过通用城市选择组件提供选择体验，并直接提交到用户 `city` 字段。
- 字典项若被业务表引用则禁止删除，返回 409。
- 用户关注关系禁止自关注。
- 用户公开资料不暴露 `email`、`phone`、`status`、`safety_score` 等敏感字段。
- 用户的情感标签（`user_emotion_tags`）、兴趣标签（`user_interest_tags`）、风格偏好（`user_styles`）和语言偏好（`user_languages`）禁止由用户或管理员手动编辑；由系统根据听歌历史和歌单内容自动计算并更新。
- 播放历史按用户去重，同一音乐仅保留一条记录；重复播放时更新该记录的 `played_at` 并递增 `play_count`。每个用户播放历史最多保留最近 100 首不同的音乐。
- VIP 功能（含 VIP 用户与 VIP 音乐）当前暂不开发。
- 等级系统的 `level_config` 表由触发器驱动，种子数据位于 `planning/sql/seed_level_config.sql`，共 11 级（0~10），经验值曲线前缓后陡。
- **歌单收藏权限**：用户可以收藏**他人**的公开歌单；**禁止收藏自己的歌单**（前后端均需校验）。私密歌单不允许收藏。若用户先前收藏了公开歌单，之后该歌单被改为私密，**保持收藏关系不变**，仅前端限制不可点入查看详情和听歌。
- **歌曲收藏语义**：歌曲是否被用户收藏，**不是**独立的收藏系统，而是派生关系——当且仅当该歌曲存在于用户**任一**歌单（含系统默认「我喜欢的音乐」）中，即视为已收藏。专辑收藏、歌单收藏仍为独立关系，不受此规则影响。
- **收藏数语义**：`collect_count` 表示"累计被收藏次数"。"用户将歌曲加入自己的任意歌单"即为"收藏了该歌曲"。`collect_count` **只增不减**，从歌单移除歌曲或删除歌单时，不减少 `collect_count`，避免引入"是否仍处于收藏态"的复杂确认机制。
- **歌曲收藏前端交互**：用户点击歌曲「收藏」时，应弹出歌单选择器，让用户选择加入哪个歌单（可勾选/取消多个歌单）；**禁止**不经选择直接提示「收藏成功」。已收藏状态下再次点击，仍打开同一歌单选择器以管理归属。

## 9. 代码规范

- 后端分层：路由（`api/v1/endpoints`）→ 业务服务（`services`）→ 模型（`models`）。
- 业务异常统一使用 `BusinessError`，携带 `detail` 和建议 HTTP 状态码。
- FastAPI 依赖注入使用 `Annotated` 简写：`SessionDep`、`CurrentUser`、`ActiveUser`、`AdminUser`。
- Pydantic Schema 统一使用 `ConfigDict(from_attributes=True)`。
- 测试数据库强制指向 `echomemory_test`，由 `conftest.py` 自动替换。
- **docstring 规范**：后端所有正式方法必须编写中文 docstring，内容包含：**函数作用、入参说明、出参说明、错误处理说明**。`__init__.py` 文件若仅为空包标记，不强制 module docstring。测试类和方法可简单编写 docstring（说明测试意图即可），不强求完整四要素格式。

## 10. 前端交互规范

- 前端表单校验（如用户名长度、邮箱格式、密码长度等）由后端统一负责，后端返回错误后前端再弹出通知提示。
- 前端**不**在输入框旁用灰色字体提前显示校验规则提示（如"长度限制……"），避免干扰用户输入体验。
- **设计参考原则**：前端页面设计优先参考网易云音乐、QQ 音乐等主流音乐平台的成熟交互与布局（路由分布、详情页信息层级、列表与评论区顺序、播放器与导航结构等），在不直接复刻的前提下保证体验合理、观感专业。典型详情页内容顺序：头部信息 → 核心内容（曲目列表 / 推荐）→ 评论区。
- **歌曲收藏交互**：与主流音乐平台一致，收藏歌曲 = 加入歌单；收藏按钮触发歌单选择弹窗，而非一键收藏。

## 11. 私信与通知

- **数据模型分离**：使用 `notifications`（系统生成、不可回复）、`conversations`（私信会话元数据，反规范化最后一条消息 id 与未读数）、`direct_messages`（消息条目，挂在 conversation 下）三张独立表。禁止合并到单一 inbox 表。
- **私信权限**：任意 ACTIVE 用户可向任意 ACTIVE 用户发首条消息；接收方可一键屏蔽（`user_blocks` 表，主键 `(blocker_id, blocked_id)`），屏蔽后被屏蔽方写入消息直接 403。
- **官方账号**：`users` 表新增 `is_official BOOLEAN DEFAULT FALSE`；前端展示官方徽标。仅 SUPER_ADMIN 可置位，首期不暴露 UI，由 SQL/admin 手工置位。
- **通知事件首期范围**：被关注、评论被回复、评论被点赞、空间动态被点赞、空间动态被评论。其余事件后续按需扩展。
- **通知幂等**：同一 (recipient, actor, type, target) 重复触发不再次入库，以唯一约束（仅未读时生效）实现。取消点赞/取消关注不撤回已发出的通知。
- **自我事件不发通知**：自己给自己的评论点赞、自己回复自己评论等不产生通知。
- **实时性**：使用 WebSocket 推送（路径 `/v1/ws/inbox`，query 携带 access token，服务端复用 JWT 解码与黑名单校验）；多进程通过 Redis Pub/Sub 广播。断线时不影响正确性——所有事件已落库，前端重连后拉取增量。
- **主页面架构**：路由 `/messages`，左侧会话列表（含『通知中心』作为虚拟会话项 + 真实私信会话），右侧根据选中渲染通知列表或聊天面板。铃铛入口为下拉 Popover 含两个 Tab，底部「查看全部」跳转 `/messages`。
- **消息内容**：首期仅支持纯文本（`content TEXT NOT NULL`，长度上限 2000 字符），不预留 attachments / message_type 字段；后续如需多媒体再独立扩展。

## 12. 热度系统

- 音乐热度 = ln(近7天播放×10 + 收藏×5 + 评论×3 + 1) × 100 ÷ age_days^0.6，钳位 0~1000。
- 专辑/歌单热度 = 所含音乐 hot 的平均值。
- 播放、收藏（加入歌单）、评论（仅 music 类型）时触发单首重算。
- 歌曲加入/移出专辑或歌单时触发对应专辑/歌单热度重算。
- 后台每 4 小时全量重算（分批 200 首/0.5s），实现时间衰减；应用启动时立即执行一次。
- 热歌榜按 hot 排序，新歌榜按 hot 排序且限定近 30 天发布。

## 13. 用户 like_count

- `User.like_count` = 该用户所有评论获赞数 + 该用户所有空间说说获赞数，后端自动维护。
- 评论被点赞时 +1，取消点赞时 -1（防负保护）。
- 空间说说被点赞时 +1，取消点赞时 -1（防负保护）。

## 14. 用户 last_login_at

- 登录成功（`authenticate_user`）时写入当前 UTC 时间。

## 15. 评论排序

- 评论列表支持三种排序：`recommended`（综合：精选优先 → 最新）、`latest`（最新）、`likes`（点赞最多）。
- `recommended` 排序 = `is_recommended=TRUE` 的评论置顶（按 created_at 倒序），其余评论按 created_at 倒序。
- `Comment.is_recommended` 暂不自动维护，后续由推荐系统评估；当前仅提供排序机制和字段，管理员可手动设置。

## 16. 空间动态转发

- 用户可以转发已有的说说（`space_post`）、音乐（`music`）、专辑（`album`）、歌单（`playlist`）到自己的空间。
- 转发时创建新 SpacePost，`post_type='forward'`，设置 `source_id` 和 `source_type`。
- 转发时递增源实体的 `forward_count`（SpacePost、Music、Album、Playlist 均需有该字段）。
- Music、Album、Playlist 模型需新增 `forward_count` 字段（BigInteger, default=0, CHECK >= 0）。

## 17. 管理仪表盘

- 管理概览页展示真实统计数据：用户总数、音乐总数、专辑/歌单/评论/动态数。
- 提供后端统计聚合接口。

## 18. 暂不开发

- AI 回声（EchoPage）及 Agent 相关功能。
- `Comment.safety` 自动评估。
- 用户 `exp`/`level` 的 DB trigger（决策 #6 提及，待确认迁移中是否存在）。
