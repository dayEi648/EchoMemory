# echomemory 反直觉决策

> 本文档只记录同时满足以下条件的决策：
>
> 1. 不符合常规直觉，其它开发者或 AI 容易误判为 bug、遗漏或历史包袱；
> 2. 不属于普通项目信息，比如 API 契约、Schema 说明等；
> 3. 已经过用户明确确认，应作为后续开发约束遵守。

本文档不是项目概览、不是需求清单、不是实现索引，也不记录“正常代码本来就该这样写”的内容。能从其它专门文档、代码、测试或 API 文档自然获得的信息，不应重复写在这里。

---

## 维护规则

### 什么时候阅读

开发前应快速查看本文档，尤其当你准备“修正”某个看起来反直觉的实现时，必须先确认这里是否已经记录为用户确认过的决策。

### 什么时候更新

只有在以下情况才更新本文档：

- 用户明确确认了一项反直觉、非常规、容易被误改的长期决策。
- 用户明确改变或废弃了本文档中的某项决策。
- 开发过程中发现某个实现看似错误，但用户确认这是刻意设计，且后续很可能再次被误判。

### 不要写入

- 普通项目背景、技术栈、目录结构。
- 符合常规工程规范的实现。
- API 契约、Schema、数据库表结构、前端调用方式、错误码清单。
- 临时 TODO、修复计划、排期、实现步骤。
- 未经用户确认的推测。
- “关键位置”“相关文件”“同步清单”等实现索引。

## 已确认决策

### 播放历史不是播放事件日志

播放历史表示“用户最近播放过的 100 首不同歌曲”，同一用户对同一首歌重复播放时累计 `play_count`。

不要把它当作逐次播放事件表，也不要把“最近 100 条”理解成最近 100 次播放事件。

### “我喜欢的音乐”是系统歌单，但不是普通系统锁定项

每个用户都有唯一的“我喜欢的音乐”歌单。它承担喜欢音乐的展示容器角色，但用户可以改名，也可以设置公开或私密。

不要因为它是系统歌单就禁止改名或强制私密；但它仍然不能被删除。

### 音乐喜欢不等于普通歌单归属

用户把歌曲加入普通歌单，不代表喜欢该音乐；从普通歌单移除歌曲，也不代表取消喜欢。

音乐喜欢以专门的喜欢关系为准；普通歌单只是整理音乐的容器。不要再把“取消喜欢”实现成从用户全部歌单中删除该歌曲。

### 每日推荐和私人雷达当前是随机且当天固化

当前阶段每日推荐 / 私人雷达采用随机生成，并在当天保持稳定。

不要把这视为临时 bug 或必须立即替换的未完成算法；这是当前数据量和阶段下用户确认过的取舍。

### `MUTED` / `RESTRICTED` 不禁止登录

用户状态中，`MUTED` 表示禁言，`RESTRICTED` 表示限制，`BANNED` 表示永久封禁。

全局登录拦截只针对 `BANNED`。不要因为用户不是完全正常状态，就在登录或全局 active-user 依赖中拒绝 `MUTED` / `RESTRICTED` 用户；具体功能限制应由对应业务入口处理。

### 主动登出只退出当前设备

用户主动点击退出登录时，只应使当前设备的 token 失效。

不要让普通登出导致所有设备同时下线。全端失效只用于修改密码、永久封禁、软删除等安全事件。

### 通知只在未读阶段去重

同类通知只在未读状态下聚合。通知一旦已读，之后发生的新同类事件应产生新通知。

不要把所有历史同类通知永久合并；已读意味着用户已经处理过旧事件。

### 关注通知的目标是关注者

关注通知中，接收者由通知的 recipient 表示；通知目标应指向发起关注的人。

不要把关注通知的目标写成接收者自己，否则用户点击通知时看到的是自己，而不是新关注者。

### Agent 监控记录不随用户删除

Agent 监控用于评估和调试 Agent 本身，不属于用户业务数据。

无论用户被软删除还是硬删除，已有 Agent 监控记录都必须完整保留。监控记录中的用户标识是运行时快照，不应通过级联外键绑定用户生命周期，也不要在用户删除时匿名化或清理。

### Agent 监控故障不得阻断主流程

Agent 监控是旁路可观测性设施。监控写入失败时，Agent 主流程必须继续执行。

监控写入应使用独立异步队列和有限重试；重试后仍失败时写入系统错误日志，但不要把监控异常传播给 Graph、Chain、工具调用或用户侧流式响应。
