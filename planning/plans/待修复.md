     ```python
     if playlist is None or playlist.is_private:
     ```

### 2. 收藏数维护不完整，且存在不应有的递减操作

位置：

- `apps/backend/src/echomemory_backend/services/collection_service.py:50`
- `apps/backend/src/echomemory_backend/services/collection_service.py:78`
- `apps/backend/src/echomemory_backend/services/collection_service.py:153`
- `apps/backend/src/echomemory_backend/services/collection_service.py:181`
- `apps/backend/src/echomemory_backend/services/collection_service.py:252`
- `apps/backend/src/echomemory_backend/services/collection_service.py:282`
- `apps/backend/src/echomemory_backend/services/playlist_service.py:298`
- `apps/backend/src/echomemory_backend/services/playlist_service.py:346`
- `apps/backend/src/echomemory_backend/services/playlist_service.py:384`

问题：

- 用户显式收藏音乐/专辑/歌单时没有维护对应 `collect_count`。
- `remove_music_from_playlist` 和 `delete_playlist` 却减少了 `music.collect_count`，与"只增不减"的设计决策冲突。

**设计决策（已确认）**：

- "用户将歌曲加入自己的任意歌单"即为"收藏了该歌曲"。
- `collect_count` 表示"累计被收藏次数"，**只增不减**。
- 从歌单移除歌曲或删除歌单时，不减少 `collect_count`，避免引入"是否仍处于收藏态"的复杂确认机制。

修复方案：

1. 修改 `collection_service.py`：
   - `collect_music` 在 `db.add(collection)` 后、`await db.commit()` 前，执行原子 UPDATE 递增 `music.collect_count`：
     ```python
     from sqlalchemy import update
     await db.execute(
         update(Music).where(Music.id == music_id).values(collect_count=Music.collect_count + 1)
     )
     ```
   - `collect_album` 同理递增 `album.collect_count`。
   - `collect_playlist` 同理递增 `playlist.collect_count`。
   - `uncollect_music` / `uncollect_album` / `uncollect_playlist` **不**执行递减操作（符合只增不减决策）。
2. 修改 `playlist_service.py`：
   - `add_music_to_playlist` 中保留 `music.collect_count += 1`（或改为原子 UPDATE），因为"加入歌单=收藏"。
   - `remove_music_from_playlist` 中**删除** `music.collect_count -= 1`。
   - `delete_playlist` 中**删除**遍历歌单内歌曲并递减 `music.collect_count` 的逻辑。
3. 补充单元测试，断言收藏/加入歌单后 `collect_count` 正确递增；断言移除歌曲/删除歌单后 `collect_count` 不变。

### 3. 计数类字段存在并发丢失更新和负数风险

位置：

- `apps/backend/src/echomemory_backend/services/comment_service.py:156`
- `apps/backend/src/echomemory_backend/services/comment_service.py:160`
- `apps/backend/src/echomemory_backend/services/comment_service.py:238`
- `apps/backend/src/echomemory_backend/services/comment_service.py:250`
- `apps/backend/src/echomemory_backend/services/comment_service.py:278`
- `apps/backend/src/echomemory_backend/services/comment_service.py:297`
- `apps/backend/src/echomemory_backend/services/comment_service.py:325`
- `apps/backend/src/echomemory_backend/services/comment_service.py:344`
- `apps/backend/src/echomemory_backend/services/playlist_service.py:346`
- `apps/backend/src/echomemory_backend/services/playlist_service.py:384`

问题：

- 多处使用 ORM 对象 `+= 1` / `-= 1` 更新计数，并发请求下可能丢失更新。
- 取消点赞、删除评论等路径没有在应用层防止计数减到负数。
- 数据库虽然有部分非负约束，但触发后会变成 500 或未统一转换的数据库错误。

修复方案：

1. 将 `comment_service.py` 中所有 ORM 对象级计数修改替换为 SQLAlchemy 原子 `update`：
   - `create_comment` 中 `target.comment_count += 1` 替换为：
     ```python
     await db.execute(
         update(target_cls)
         .where(target_cls.id == target_id)
         .values(comment_count=target_cls.comment_count + 1)
     )
     ```
   - 同理替换 `parent.reply_count += 1`、所有 `-= 1` 操作。
2. 所有递减 UPDATE 增加 `WHERE count > 0` 防负保护，例如：
   ```python
   await db.execute(
       update(Comment)
       .where(Comment.id == comment_id, Comment.like_count > 0)
       .values(like_count=Comment.like_count - 1)
   )
   ```
3. 对 `playlist_service.py` 中 `add_music_to_playlist` 的 `music.collect_count += 1`（修复问题 2 时若保留）同样替换为原子 UPDATE。
4. 补充并发安全测试：连续多次点赞/取消点赞后计数正确；重复取消点赞后计数不为负。

### 4. 文件上传校验不足，存在内存和文件类型安全风险

位置：

- `apps/backend/src/echomemory_backend/core/image_utils.py:8`
- `apps/backend/src/echomemory_backend/core/image_utils.py:60`
- `apps/backend/src/echomemory_backend/core/oss_client.py:88`
- `apps/backend/src/echomemory_backend/api/v1/endpoints/music.py:17`
- `apps/backend/src/echomemory_backend/api/v1/endpoints/music.py:75`
- `apps/backend/src/echomemory_backend/api/v1/endpoints/music.py:121`
- `apps/backend/src/echomemory_backend/api/v1/endpoints/space_post.py:14`
- `apps/backend/src/echomemory_backend/api/v1/endpoints/space_post.py:37`
- `apps/backend/src/echomemory_backend/api/v1/endpoints/space_post.py:46`

问题：

- 图片上传只检查 `content_type.startswith("image/")`，没有读取前的输入大小限制，也没有显式处理 Pillow decompression bomb。
- `compress_image_to_memory` 的最终回退不再确认输出一定小于 `MAX_IMAGE_SIZE_BYTES`。
- 音频/歌词校验主要依赖客户端声明的 `content_type`，没有内容签名或扩展名白名单。
- `_safe_ext` 直接接受上传文件名扩展名，可能生成与实际内容不匹配的 OSS object key。

**设计决策（已确认）**：

- 图片上传：初始文件最大 **10MB**，后端压缩至 **≤2MB** 后再发送至 OSS。
- 音频上传：最大 **30MB**。
- 歌词上传：最大 **1MB**。

修复方案：

1. 修改 `image_utils.py`：
   - 模块顶部增加 Pillow decompression bomb 防护：
     ```python
     import warnings
     Image.MAX_IMAGE_PIXELS = 89_478_485  # ~9500x9500
     warnings.simplefilter('error', Image.DecompressionBombWarning)
     ```
   - `compress_image_to_memory` 开头增加输入大小检查（最大 10MB）：
     ```python
     file.seek(0, 2)
     input_size = file.tell()
     file.seek(0)
     if input_size > 10 * 1024 * 1024:
         raise ValueError("Image file exceeds 10MB limit")
     ```
   - 最终回退后增加输出大小断言：
     ```python
     if buffer.tell() > max_size:
         raise ValueError("Unable to compress image to target size")
     ```
2. 修改 `oss_client.py`：
   - 将 `_MAX_AUDIO_SIZE_BYTES` 从 20MB 改为 **30MB**。
   - `_upload_file_to_oss_sync` 在 content_type 校验后，增加扩展名白名单校验（拒绝 `.exe`, `.bat`, `.sh` 等危险扩展名）。
   - 音频/歌词上传时，扩展名由服务端根据 `content_type` 映射决定（如 `audio/mpeg` -> `mp3`），不再直接使用 `_safe_ext` 的结果作为 OSS key 扩展名；`_safe_ext` 仅作为兜底参考。
   - 可选：引入 `python-magic` 进行文件内容签名探测（若允许新增依赖），不信任客户端声明的 MIME。
3. 修改 `music.py` 和 `space_post.py`：
   - 将 `_safe_ext` 扩展名限制在白名单内（如 `{"mp3", "flac", "wav", "ogg", "aac", "lrc", "jpg", "jpeg", "png"}`），不在白名单时回退到默认扩展名。

### 6. 异步生命周期里调用阻塞 `subprocess.run`

位置：

- `apps/backend/src/echomemory_backend/main.py:113`

问题：

- `lifespan` 是 async context，但启动迁移使用同步 `subprocess.run`。应用启动期间会阻塞事件循环。
- 当前决策允许启动时自动 Alembic，但"全面异步服务"要求运行时避免阻塞调用。

修复方案：

1. 修改 `main.py` 的 `lifespan`：
   - 将 `subprocess.run(...)` 替换为线程池执行：
     ```python
     import asyncio
     result = await asyncio.to_thread(
         subprocess.run,
         [sys.executable, "-m", "alembic", "upgrade", "head"],
         capture_output=True,
         text=True,
         cwd=str(base_dir),
     )
     ```
   - 失败时先记录日志再抛异常：
     ```python
     if result.returncode != 0:
         logger.error("Alembic upgrade failed: %s", result.stderr)
         raise RuntimeError(f"Alembic upgrade failed: {result.stderr}")
     ```
2. 备选方案（推荐）：将 Alembic 迁移从应用 `lifespan` 中移除，前置到 Dockerfile 的 `ENTRYPOINT` 或独立启动脚本（如 `scripts/start.sh`）中执行，保持 FastAPI 应用启动过程纯粹异步。

### 7. 异常处理风格不统一，部分错误可能暴露内部细节

位置：

- `apps/backend/src/echomemory_backend/main.py:131`
- `apps/backend/src/echomemory_backend/api/v1/endpoints/auth.py:94`
- `apps/backend/src/echomemory_backend/api/v1/endpoints/album.py:95`
- `apps/backend/src/echomemory_backend/api/v1/endpoints/playlist.py:65`
- `apps/backend/src/echomemory_backend/services/music_service.py:245`
- `apps/backend/src/echomemory_backend/services/album_service.py:233`
- `apps/backend/src/echomemory_backend/services/album_service.py:385`

问题：

- 全局异常处理器只覆盖 `BusinessError`，但大量 endpoint 又捕获 `BusinessError` 并转成 `HTTPException`，绕开统一处理器。
- 多个 service 把底层 `IntegrityError` 原文拼入对外 `BusinessError.detail`，可能暴露 SQL、约束名或内部结构。
- 对 `RuntimeError`、`SQLAlchemyError`、未知异常没有统一日志和对外错误格式。

修复方案：

1. 修改 `main.py`，增加通用异常处理器：
   ```python
   from fastapi.exceptions import RequestValidationError
   from fastapi.responses import JSONResponse
   from starlette.exceptions import HTTPException as StarletteHTTPException
   import logging

   logger = logging.getLogger(__name__)

   @app.exception_handler(StarletteHTTPException)
   async def http_exception_handler(request: Request, exc: StarletteHTTPException):
       return JSONResponse(status_code=exc.status_code, content={"detail": exc.detail})

   @app.exception_handler(RequestValidationError)
   async def validation_exception_handler(request: Request, exc: RequestValidationError):
   ```

### 12. 事务边界存在部分成功风险

位置：

- `apps/backend/src/echomemory_backend/services/play_history_service.py:75`
