## 🔴 Critical（1 项）

### 1. `get_current_active_user` 只拦截 `BANNED(3)`，`TEMP_BAN(1)` 和 `SUSPENDED(2)` 用户可畅通无阻

- **文件**：`api/deps.py:102-109`
- **现象**：

```python
async def get_current_active_user(current_user: CurrentUser) -> User:
    if current_user.status == UserStatus.BANNED:  # ← 仅检查 == 3
        raise HTTPException(...)
    return current_user
```

`UserStatus` 定义为 `ACTIVE=0, TEMP_BAN=1, SUSPENDED=2, BANNED=3`。当管理员通过 `UserBanAction(status=1或2)` 封禁用户后，该用户仍可通过所有需要 `ActiveUser` 的端点（评论、收藏、歌单操作、动态发布等 10+ 个端点）。

- **修复**：

```python
if current_user.status != UserStatus.ACTIVE:
    raise HTTPException(
        status_code=status.HTTP_403_FORBIDDEN,
        detail="User account is not active",
    )
```

## 🟠 Important（5 项）

### 2. 音乐/歌单/专辑导入接口未捕获 `BusinessError`，导致已上传 OSS 文件成为孤儿

- **文件**：`api/v1/endpoints/music.py:171-179`、`playlist.py:59-68`、`album.py:74-84`
- **现象**：`import_music` 的异常捕获链只覆盖了 `HTTPException` 和 `(RuntimeError, ValueError, IntegrityError, SQLAlchemyError)`，但 `create_music` → `_set_music_authors` → `validate_*_exist` 均可抛出 `BusinessError`。`BusinessError` 直接继承 `Exception`，不在上述捕获范围内，因此穿透后 OSS 文件已上传但不会被清理。

```python
except HTTPException:
    cleanup(); raise
except (RuntimeError, ValueError, IntegrityError, SQLAlchemyError):
    cleanup(); raise
# BusinessError 直接穿透！→ OSS 孤儿文件
```

- **影响**：每次触发此路径都会在 OSS 中留下一个或多个无法被引用的文件，持续产生存储费用。
- **修复**：增加 `BusinessError` 到捕获列表，或简化为：

```python
except HTTPException:
    cleanup; raise
except Exception:
    cleanup; raise
```

> 注意：`playlist.py` 创建端点和 `album.py` 创建端点存在相同模式，需一并修复。

### 3. `source or None` 模式导致管理员无法清空 `source` 字段

- **文件**：`api/v1/endpoints/music.py:158`（endpoint 层）、`services/music_service.py:498`（service 层）
- **现象**：

```python
# endpoint: source="" → None（因为 or None）
source=source or None,

# service: None → 跳过修改
if source is not None:
    music.source = source
```

管理员传 `source=""` 意图清空该字段，但被 `or None` 转为 `None`，service 层将其理解为"不修改此字段"。该字段永远无法通过 API 清空。

- **修复**：去掉 `or None`，直接传递原始值：

```python
# endpoint 层
source=source,  # None = 不修改（未传）, "" = 清空

# service 层无需修改即可正确处理
```

### 4. Carousel 操作存在 read-modify-write 并发竞态

- **文件**：`services/carousel_service.py:91-173`
- **现象**：`update_carousel_item`、`delete_carousel_item`、`reorder_carousel_items` 均执行 `lrange → 本地修改 → delete → rpush`。两个并发的管理员操作会互相覆盖：

```
A: lrange → [a, b, c]       B: lrange → [a, b, c]
A: 删除 a → rpush [b, c]
                             B: 删除 c → rpush [a, b]  ← a 复活了！
```

- **修复**：使用 Redis `LREM` 直接按值删除（delete），或编写 Lua 脚本将读-改-写包装为原子操作。

### 5. 点赞/关注/动态点赞的通知创建与业务操作在不同事务中

- **文件**：`services/comment_service.py:387-405`、`services/user_service.py:186-201`、`services/space_post_service.py:191-206`
- **现象**：以 `like_comment` 为例：

```python
db.add(CommentLike(...))
await db.execute(update(Comment).values(like_count=Comment.like_count + 1))
await db.commit()            # ① 点赞记录 + 计数已提交

await create_notification(...)  # ② flush 通知（未提交）
await db.commit()            # ③ 提交通知
```

若步骤③失败（如 DB 连接断开），点赞已持久化但通知丢失。虽然项目决策中声明"通知尽力而为"，但将通知放在第一个 `commit()` 之前不会增加额外风险，反而消除了不必要的分裂。

- **修复**：将通知创建移到第一个 `commit()` 之前：

```python
db.add(CommentLike(...))
await db.execute(update(Comment).values(like_count=Comment.like_count + 1))

if comment.user_id != user_id:
    await create_notification(...)  # flush，不 commit

await db.commit()  # 一次性提交业务操作 + 通知
```

## 🟡 Minor（6 项）

### 7. `delete_playlist` 中 `hasattr` 检查无实际保护作用

- **文件**：`services/playlist_service.py:460`
- **现象**：

```python
if hasattr(playlist, "musics") and playlist.musics:
    for pm in list(playlist.musics):
        await db.delete(pm)
```

SQLAlchemy relationship descriptor 在类层面始终存在，`hasattr` 永远为 `True`，此检查形同虚设。若未来某调用方未 preload musics，`playlist.musics` 会触发意外懒加载甚至 `DetachedInstanceError`。

- **修复**：使用 `sqlalchemy.inspect(playlist).unloaded` 准确判断关系是否已加载。

### 8. WebSocket 端点无心跳/超时机制

- **文件**：`api/v1/endpoints/ws_inbox.py:69-127`
- **现象**：客户端异常断网（未发 close frame）时，服务端 PubSub 订阅和 forward task 持续占用资源直到 TCP keepalive 超时（通常 2 小时）。
- **修复**：添加 30 秒间隔的 ping/pong 心跳协程，超时主动关闭连接。
