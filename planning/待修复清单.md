## 1. 前端：`DiscoverPage` 的错误兜底改造引入 TypeScript 构建失败

- **问题**：`DiscoverPage.tsx` 将多个不同返回类型的请求放入 `Promise.allSettled()` 后，又通过 `results.map(...)` 统一生成兜底值。TypeScript 会把 `hotRes`、`newRes`、`playlistRes`、`albumRes`、`chartRes`、`carouselRes` 推断为多个响应类型的联合类型，其中包含 `CarouselItem[]`，因此后续访问 `.items` 会报错。
- **影响**：`npm run build` 无法通过，前端当前不可交付。单元测试通过不能覆盖该问题，因为 `npm test` 不执行完整 TypeScript 构建。
- **修复位置**：
  - `apps/frontend/src/pages/DiscoverPage.tsx:138-170`
- **修复思路**：
  1. 不要对异构结果数组使用统一 `map` 兜底。应逐项解包 `PromiseSettledResult`，让每个变量保留明确类型。
  2. 可新增局部 helper，例如 `settledValue(result, fallback)`，但调用点必须逐项写清楚：
     - 热歌、新歌：兜底 `{ items: [], total: 0 }`
     - 推荐歌单、推荐专辑：兜底 `{ items: [], total: 0 }`
     - 推荐榜：兜底 `{ items: [] }`
     - 轮播图：兜底 `[]`
  3. 修复后保留“部分内容加载失败”的 toast，但不要为了减少代码行数牺牲类型可读性。
- **验收标准**：
  - `npm run build` 通过。
  - `npm test` 通过。
  - `DiscoverPage` 任一单独请求失败时，其余区块仍能渲染成功数据。
  - 轮播图请求失败时不影响歌曲、歌单、专辑、推荐榜展示。

## 2. 前端：管理员降级后的后台权限校验仍不完整

- **问题**：当前 `AdminRouteGuard` 只在组件挂载时调用一次 `refreshUser()`。如果管理员已经停留在管理后台，之后账号被远端降级，前端不会主动再次校验，仍可能继续停留在管理后台。另一个隐患是 `authStore.refreshUser()` 捕获异常后静默失败并保留旧 `user`，401/403 或获取用户失败时可能继续使用旧管理员状态。
- **影响**：管理员权限变更存在生效延迟。虽然后端接口仍应做权限校验，但前端仍会展示后台入口和后台页面，带来越权操作体验和安全边界误导。
- **修复位置**：
  - `apps/frontend/src/App.tsx:136-169`
  - `apps/frontend/src/shared/stores/authStore.ts:109-115`
- **修复思路**：
  1. 将管理员区域的权限校验设计为“进入时校验 + 停留期间定期或事件触发校验”。
  2. 推荐在 `AdminRouteGuard` 或管理后台外壳组件中增加轻量轮询，例如每 30-60 秒调用一次 `refreshUser()`；也可在窗口重新聚焦、路由变化、关键后台操作前触发校验。
  3. 调整 `refreshUser()` 的错误处理语义：遇到 401 应清 token 并置空 `user`；遇到 403 或返回用户角色不再是管理员时，管理后台应立即重定向到首页。网络错误可以保留当前用户，但需要让调用方知道刷新失败，避免把失败误当作校验通过。
  4. 避免在 render 阶段依赖 `useAuthStore.getState()` 读取快照来绕过订阅；优先使用 hook 订阅到的 `user` 状态，保证状态变化会触发重渲染。
- **验收标准**：
  - 以管理员身份进入 `/admin` 后，后端 `/auth/me` 返回普通用户时，前端会自动跳转到 `/`。
  - `refreshUser()` 收到 401 时会清理登录态，不再保留旧管理员状态。
  - 管理后台停留期间远端角色变更，无需手动刷新即可在下一次校验后生效。
  - 新增测试覆盖“初始为管理员，后续刷新返回普通用户时被踢出后台”。

## 3. 前端：错误提示改造覆盖不全，且状态码兜底逻辑可能被通用 message 截断

- **问题**：本轮修复只覆盖了清单点名的一部分普通页面，项目中仍存在大量 `toast.error(err.message)` 或静默吞错，例如后台管理页、搜索页、账号页、创建歌单弹窗等。新增的 `getApiErrorMessage()` 也存在逻辑顺序问题：当 `ApiError` 没有业务错误码、但 `message` 是通用“请求失败”时，会优先返回该通用 message，导致后续 401/403/404/409/422 等状态码差异化提示不会生效。
- **影响**：用户仍可能看到原始英文、通用“请求失败”，或完全没有错误提示。关键操作失败时无法明确区分登录过期、无权操作、资源不存在、冲突、参数错误等情况。
- **修复位置**：
  - `apps/frontend/src/shared/apiError.ts`
  - `apps/frontend/src/pages/AccountPage.tsx`
  - `apps/frontend/src/pages/BrowsePage.tsx`
  - `apps/frontend/src/pages/SearchPage.tsx`
  - `apps/frontend/src/pages/PlaylistsPage.tsx`
  - `apps/frontend/src/pages/SpacePage.tsx`
  - `apps/frontend/src/pages/admin/*.tsx`
  - `apps/frontend/src/components/ui/AddToPlaylistModal.tsx`
  - `apps/frontend/src/components/ui/CreatePlaylistModal.tsx`
  - `apps/frontend/src/components/ui/CreatePostForm.tsx`
- **修复思路**：
  1. 先修正 `getApiErrorMessage()` 的优先级：
     - 业务错误码有明确描述时优先返回错误码描述。
     - 非信封错误或未知业务码时，先按 HTTP 状态码返回中文兜底。
     - 只有状态码也无法识别时，再返回后端 `msg` / `message` / fallback。
  2. 用 `getApiErrorMessage(err, "...失败")` 替换关键页面中的 `err instanceof Error ? err.message : ...`。
  3. 清理不合理的静默吞错。对后台统计、歌单列表、搜索、收藏、删除、发布等用户可感知操作，应至少给出 toast；对音频自动播放这类浏览器策略导致的失败，可以保留静默或注释说明。
  4. 增加 `apiError` 单元测试，覆盖业务错误码、401、403、404、409、422、429、未知错误码、非 ApiError 等路径。
- **验收标准**：
  - `rg "toast\\.error\\((err|error)\\.message|err instanceof Error \\? err\\.message|catch\\(\\(\\) => \\{\\}\\)|silently fail" apps/frontend/src` 中不再出现关键业务操作的未处理项；确需静默的地方有明确注释。
  - 401 显示“登录已过期，请重新登录”，403 显示“无权执行此操作”，404 显示“资源不存在”，409 显示冲突提示，422 显示参数错误提示。
  - `npm test` 通过。
  - `npm run build` 通过。
