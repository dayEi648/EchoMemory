## 1. `User.created_at` 只改了模型，Alembic 迁移没有同步

- **位置**
  - `apps/backend/src/echomemory_backend/models/user.py:64`
  - `apps/backend/alembic/versions/d7f56266b3f3_init_schema_and_seed_level_config.py:171`
- **现状**
  - ORM 模型中 `User.created_at` 已改为 `Mapped[datetime]` 且显式 `nullable=False`。
  - 但初始 Alembic 迁移仍创建 `users.created_at` 为 `nullable=True`。
- **影响**
  - 测试环境使用 `Base.metadata.create_all()`，会按最新模型创建非空列，因此测试通过不能证明迁移后的真实数据库一致。
  - 生产/开发库通过 Alembic 升级时，已有表结构不会因为模型变更自动修改，最终会出现模型与数据库 schema 漂移。
- **修复建议**
  - 新增 Alembic 迁移，不直接改旧迁移文件。
  - 迁移中先将历史空值回填为 `now()` 或合理的默认时间，再执行 `op.alter_column("users", "created_at", nullable=False, existing_type=sa.DateTime(timezone=True))`。
  - downgrade 中恢复 `nullable=True`。
- **验收标准**
  - `alembic upgrade head` 可在已有数据库上成功执行。
  - 数据库中 `users.created_at` 为 `NOT NULL`。
  - 模型、测试建表结果、Alembic 升级结果三者一致。

## 2. 通知去重索引迁移缺少历史重复数据清理

- **位置**
  - `apps/backend/alembic/versions/e8f3a2b1c4d5_fix_notification_null_actor_dedupe.py:21`
  - `apps/backend/src/echomemory_backend/models/notification.py:87`
  - `apps/backend/src/echomemory_backend/services/notification_service.py:73`
- **现状**
  - 新模型与服务层已将通知去重拆为两类：
    - `actor_id IS NOT NULL`：按 `recipient_id, actor_id, type, target_type, target_id` 去重。
    - `actor_id IS NULL`：按 `recipient_id, type, target_type, target_id` 去重。
  - 新迁移直接创建 `uq_notifications_dedupe_unread_system` 唯一索引。
- **影响**
  - 旧索引包含 `actor_id`，在 PostgreSQL 中多个 `NULL` 不冲突，因此历史库里可能已经存在重复未读系统通知。
  - 如果存在这些重复数据，新迁移在创建系统通知唯一索引时会失败，导致应用启动时自动 Alembic 升级失败。
- **修复建议**
  - 在创建 `uq_notifications_dedupe_unread_system` 前增加数据清理 SQL。
  - 推荐保留每组重复未读系统通知中最早或最新的一条，删除其余记录。分组键为：
    - `recipient_id`
    - `type`
    - `target_type`
    - `target_id`
    - 条件：`is_read = false AND actor_id IS NULL`
  - 清理后再创建两个部分唯一索引。
  - 若需要保留审计信息，也可以把重复通知先标记为已读，而不是删除；但需要明确这是产品上可接受的行为。
- **验收标准**
  - 构造一组重复未读系统通知后，`alembic upgrade head` 仍能成功。
  - 升级后同一系统通知只能存在一条未读记录。
  - `create_notification(actor_id=None, ...)` 重复调用保持幂等。

## 3. 422 校验错误详情可能包含不可 JSON 序列化对象

- **位置**
  - `apps/backend/src/echomemory_backend/core/exceptions/handlers.py:90`
  - `apps/backend/src/echomemory_backend/schemas/user.py:98`
- **现状**
  - `validation_exception_handler` 直接将 `exc.errors()` 放入 `JSONResponse` 的 `content`。
  - Pydantic 字段校验器抛出 `ValueError` 时，`exc.errors()` 可能包含 `ctx: {"error": ValueError(...)}`。
- **影响**
  - 标准 JSON 编码器无法序列化 `ValueError` 对象。
  - 某些本应返回 422 的请求会在异常处理器中再次失败，最终表现为 500。
  - 已确认示例：`UserBanAction(status=1, ban_duration="bad")` 产生的 `exc.errors()` 中包含 `ValueError` 对象，`json.dumps({"errors": exc.errors()})` 会报 `TypeError: Object of type ValueError is not JSON serializable`。
- **修复建议**
  - 在错误响应前使用 FastAPI 的 `jsonable_encoder(exc.errors())`。
  - 或者显式清洗 `errors`，将 `ctx.error` 转成字符串。
  - 推荐使用 `jsonable_encoder`，因为它能统一处理更多非 JSON 原生类型。
- **验收标准**
  - 提交非法 `ban_duration` 时返回 422，而不是 500。
  - 响应信封中仍包含字段级错误详情。
  - 新增测试覆盖带自定义 `ValueError` validator 的 422 响应。

## 4. 评论回复分页的 `total` 统计会被放大

- **位置**
  - `apps/backend/src/echomemory_backend/services/comment_service.py:351`
  - `apps/backend/src/echomemory_backend/db/pagination.py:48`
- **现状**
  - `list_replies()` 的主查询使用了 `root = aliased(Comment)` 并通过 join 校验根评论未删除。
  - 但传入通用 `paginate()` 的 `where_clause` 中包含 alias 条件，`paginate()` 重新构造 count 查询时没有保留主查询中的 join 条件。
- **影响**
  - 当前页 `items` 可能正确，但 `total` 会受其他未删除评论数量影响而被放大。
  - 前端分页器可能显示不存在的页，继续请求后出现空页或分页体验异常。
- **修复建议**
  - 不要在这个场景直接复用当前 `paginate()` 的 count 逻辑。
  - 方案一：在 `list_replies()` 内单独写 count 查询，并显式 join root alias：
    - `select(func.count()).select_from(Comment).join(root, Comment.root_id == root.id).where(...)`
  - 方案二：增强 `paginate()`，让 total 基于原始 `stmt` 去掉排序后包一层 subquery 统计，避免 join/alias 信息丢失。
  - 如果只影响该接口，优先采用方案一，改动更小。
- **验收标准**
  - 一个根评论有 2 条回复，同时库中另有多条未删除评论时，`/comments/replies/{root_id}` 的 `total` 仍为 2。
  - 根评论软删除后，`items=[]` 且 `total=0`。
  - 分页参数 `limit/offset` 不影响 `total` 准确性。
